CITS1402 Project - Bubble Trouble
testEvidence.txt - Database Detective: our own testing evidence
======================================================================

Setup for every test:
  A fresh database built with createTables.sql, createTriggers.sql,
  createViews.sql and our small hand-checked dataset (testData.sql),
  with PRAGMA foreign_keys = ON.

----------------------------------------------------------------------
TEST 1 - Rejected CHECK constraint (BR5 membership-card checksum)
----------------------------------------------------------------------
1. Testing:   A 10-digit, all-numeric card whose weighted sum is NOT
              divisible by 11 must be rejected.
2. SQL:       INSERT INTO Member
              VALUES (6, 'Test Card', 'test@example.com',
                      '5264579467', '2026-09-01');
3. Predicted: Rejected. It "looks" valid (10 digits), but
              10*5+9*2+8*6+7*4+6*5+5*7+4*9+3*4+2*6+1*7 = 276, and
              276 mod 11 = 1, not 0.
4. Actual:    Error: CHECK constraint failed: BR5_cardChecksum
              (no row inserted)
5. Why:       The GLOB test passes, but the third part of the CHECK
              (weighted sum % 11 = 0) is false, so the whole CHECK fails.

----------------------------------------------------------------------
TEST 2 - Rejected FOREIGN KEY (order for a member who does not exist)
----------------------------------------------------------------------
1. Testing:   An order cannot refer to a member that does not exist.
2. SQL:       INSERT INTO SalesOrder
              VALUES (2000, 999, 'S01', '2026-09-20', '10:00');
3. Predicted: Rejected, because there is no Member with memberId 999.
4. Actual:    Error: FOREIGN KEY constraint failed
              (no row inserted)
5. Why:       SalesOrder.memberId REFERENCES Member(memberId), and with
              foreign keys switched on SQLite refuses a value that has
              no matching parent row.

----------------------------------------------------------------------
TEST 3 - Loyalty boundary: the member's 10th drink (quantity 1)
----------------------------------------------------------------------
1. Testing:   A member who has bought exactly 9 drinks buys 1 more;
              that 10th drink must be free.
2. SQL:       -- Alice (member 1) already has 3 + 2 + 4 = 9 drinks
              INSERT INTO SalesOrder VALUES (1004, 1, 'S01', '2026-07-10', '10:00');
              INSERT INTO OrderItem  VALUES (1004, 1, 'P01', 'M', 1, NULL, NULL);
              SELECT quantity, unitPrice, lineTotal
              FROM OrderItem WHERE orderId = 1004;
3. Predicted: unitPrice = 6.00 + 0.50 = 6.50 (Trigger A),
              lineTotal = (1 - 1) * 6.50 = 0.00 (Trigger B).
4. Actual:    quantity 1 | unitPrice 6.5 | lineTotal 0.0
              (Alice's previous line, drinks 6-9, was charged in full: 26.0)
5. Why:       priorQty = 9, and 9/10 = 0 < (9+1)/10 = 1 in integer
              division, so a multiple of 10 was crossed and one drink is free.

----------------------------------------------------------------------
TEST 4 - Loyalty inside a multi-quantity line
----------------------------------------------------------------------
1. Testing:   A member with 8 previous drinks buys quantity 3, so the
              line holds drinks 9, 10 and 11; exactly one must be free.
2. SQL:       -- Bob (member 2) already has 8 drinks
              INSERT INTO SalesOrder VALUES (1008, 2, 'S02', '2026-08-15', '13:05');
              INSERT INTO OrderItem  VALUES (1008, 1, 'P04', 'L', 3, NULL, NULL);
              SELECT quantity, unitPrice, lineTotal
              FROM OrderItem WHERE orderId = 1008 AND lineNo = 1;
3. Predicted: unitPrice = 5.50 + 1.00 = 6.50,
              lineTotal = (3 - 1) * 6.50 = 13.00 (not 19.50).
4. Actual:    quantity 3 | unitPrice 6.5 | lineTotal 13.0
5. Why:       8/10 = 0 < (8+3)/10 = 1, so the threshold lies inside the
              line; a solution that only checked quantity 1 would miss this.

----------------------------------------------------------------------
TEST 5 - Zero-activity member must still appear (MemberSummary view)
----------------------------------------------------------------------
1. Testing:   A member who has never ordered must appear with zeros,
              not disappear from the view.
2. SQL:       SELECT * FROM MemberSummary WHERE memberId = 4;
3. Predicted: One row: 4 | Dana Lee | 0 | 0 | 0
4. Actual:    memberId 4 | Dana Lee | totalOrders 0 | totalDrinks 0 | totalSpent 0
              (Q3 likewise shows the new store "Joondalup Central" with 0 orders, 0 revenue)
5. Why:       The view starts FROM Member and uses LEFT JOIN, so Dana is
              kept with NULLs; COUNT(DISTINCT ...) gives 0 and COALESCE(SUM(...), 0)
              turns the NULL sums into 0.
